# ADR-0014: Runtime Configuration Architecture

- **Status:** Accepted
- **Date:** 2026-08-03
- **Decision Makers:** Kernschmied Architecture Team
- **Supersedes:** None
- **Superseded by:** None

---

# Context

Kernschmied is designed as a long-lived, schema-driven platform whose business behavior can evolve continuously without requiring application redeployment.

The platform supports runtime administration of:

- hierarchy definitions
- prompts
- resources
- widgets
- actions
- workflows
- AI models
- tool configuration
- permissions
- UI behavior
- branding
- feature configuration
- future plugins

The platform must therefore distinguish clearly between infrastructure required to start the application and configuration that defines business behavior.

Runtime configuration is expected to change frequently during operation.

Infrastructure configuration should change rarely.

---

# Problem

Many enterprise systems gradually accumulate hundreds of configuration values distributed across:

- environment variables
- configuration files
- hardcoded defaults
- application code
- databases

This leads to inconsistent behavior and makes configuration difficult to understand.

A configurable platform requires one authoritative runtime configuration architecture.

---

## Configuration Scattered Across the System

Configuration becomes distributed across many locations.

Developers no longer know which value is authoritative.

---

## Restart Required for Business Changes

Simple business configuration changes often require restarting the application.

This reduces operational flexibility.

---

## Poor Validation

Configuration stored as strings or loosely typed JSON often lacks validation.

Invalid values may only be detected at runtime.

---

## Difficult Auditing

Configuration changes are difficult to trace.

Organizations cannot determine:

- who changed a value
- when it changed
- why it changed

---

## Cache Inconsistencies

Multiple workers may operate with different configuration snapshots.

This leads to unpredictable behavior.

---

## Tight Coupling

Business logic becomes dependent upon configuration implementation details.

Configuration can no longer evolve independently.

---

# Decision

Kernschmied adopts a **Runtime Configuration Architecture**.

Business configuration is stored as structured, versioned and validated data inside the platform.

Runtime configuration becomes the authoritative source for platform behavior after bootstrap initialization.

---

# Architectural Principle

> **Bootstrap starts the platform.
>
> Runtime configuration defines platform behavior.
>
> Configuration is data, not code.**

---

# High-Level Architecture

```text
Application Start

        │

        ▼

Bootstrap Configuration

        │

        ▼

Infrastructure

        │

        ▼

Runtime Configuration Store

        │

        ▼

Configuration Service

        │

        ▼

Business Services
```

---

# Core Concepts

The Runtime Configuration Architecture consists of several independent concepts.

---

## Configuration Store

Runtime configuration is stored in the database.

Configuration is never embedded directly into application code.

Every value belongs to a well-defined configuration schema.

---

## Configuration Domains

Configuration is grouped into logical domains.

Typical examples include:

- models
- prompts
- hierarchy
- widgets
- actions
- workflows
- branding
- permissions
- integrations
- notifications

Additional domains may be introduced over time.

---

## Versioned Configuration

Every configuration object contains:

- schema version
- revision
- timestamps

Configuration evolution follows ADR-0005.

---

## Configuration Schemas

Every configuration domain is described by a versioned schema.

Schemas define:

- required properties
- optional properties
- allowed values
- validation rules
- defaults

Business logic never validates raw JSON manually.

---

## Configuration Service

All configuration access occurs through the Configuration Service.

Application code never accesses the database directly for configuration.

The Configuration Service is responsible for:

- validation
- caching
- revision handling
- authorization
- defaults
- migration support

---

## Configuration Revision

Every successful configuration change increases the corresponding revision.

Revision numbers enable:

- cache invalidation
- optimistic locking
- synchronization
- change detection

Revision numbers are monotonic.

---

## Effective Configuration

Consumers do not assemble configuration manually.

Instead, they receive an Effective Configuration generated by the Configuration Service.

Effective Configuration already contains:

- inherited values
- defaults
- overrides
- resolved references

---

## Configuration Inheritance

Some configuration domains support inheritance.

Examples include:

- prompts
- permissions
- widgets
- branding
- hierarchy settings

Inheritance behavior is explicitly defined by each contract.

---

## Configuration Scope

Configuration may exist at different scopes.

Typical scopes include:

- system
- tenant
- workspace
- hierarchy node
- user

Higher scopes provide defaults.

Lower scopes may override supported values.

---

## Dynamic Extensibility

New configuration domains may be introduced without modifying the architecture.

New schemas are registered through the Registry Architecture.

The Runtime Configuration Architecture remains unchanged.

---

# Configuration Lifecycle

Configuration follows a controlled lifecycle.

Typical states include:

- draft
- validated
- active
- deprecated
- archived

Lifecycle rules are domain-specific.

---

# Validation

Every configuration update is validated before activation.

Validation includes:

- schema validation
- business rules
- reference integrity
- compatibility checks

Invalid configuration is rejected.

---

# Activation

Validated configuration does not automatically become active.

Activation is an explicit operation.

Activation creates a new revision.

---

# Caching

Configuration may be cached.

Caches must always be invalidated using revision information.

Workers must never rely on stale configuration indefinitely.

---

# Audit Logging

Every configuration mutation is recorded.

Audit information includes:

- user
- timestamp
- affected domain
- previous revision
- new revision
- reason (if supplied)

Audit history is immutable.

---

# Authorization

Only authorized users may modify runtime configuration.

Authorization is evaluated by the backend.

Frontend applications never determine configuration permissions.

---

# Security

Runtime configuration may contain business information.

It shall never contain:

- plaintext secrets
- passwords
- API keys
- private certificates
- executable code

Secrets belong exclusively to Bootstrap Configuration or Secret Management.

---

# Configuration as Data

Runtime configuration is declarative.

Configuration describes behavior.

Configuration never contains executable logic.

The platform interprets configuration through registered implementations.

---

# Relationship to Registries

Configuration references registered definitions.

Examples include:

- model identifiers
- widget types
- action identifiers
- resource types

Configuration never embeds implementation code.

---

# Relationship to Bootstrap

Bootstrap Configuration initializes infrastructure.

Runtime Configuration initializes business behavior.

Both layers remain strictly separated.

---

# Frontend Responsibilities

The frontend may:

- display configuration
- edit configuration
- validate user input
- submit configuration changes

The frontend is never the source of truth.

---

# Backend Responsibilities

The backend is responsible for:

- validation
- persistence
- authorization
- activation
- revision management
- audit logging
- effective configuration generation

# Consequences

## Positive

### Runtime Flexibility

Business behavior can evolve without restarting the platform.

---

### Stable Architecture

Infrastructure and business configuration remain separated.

---

### Better Validation

Every configuration object follows a versioned schema.

---

### Improved Maintainability

Configuration logic becomes centralized.

---

### Better Auditability

Every configuration change is traceable.

---

### Safe Caching

Revision-based cache invalidation improves consistency.

---

### Extensibility

New configuration domains require no architectural changes.

---

## Negative

### Higher Initial Complexity

Configuration infrastructure requires additional implementation effort.

---

### Revision Management

The platform must maintain revision consistency.

---

### Schema Governance

Configuration schemas require long-term maintenance.

---

### Additional Administrative Interfaces

Runtime configuration requires dedicated management tools.

---

# Alternatives Considered

## Environment Variables for Everything

### Advantages

- Simple deployment
- Familiar approach

### Disadvantages

- Poor validation
- Restart required
- Difficult auditing
- Limited flexibility

Rejected.

---

## Configuration Files

### Advantages

- Human readable
- Easy backups

### Disadvantages

- Difficult synchronization
- Poor multi-user support
- Restart required

Rejected.

---

## Hardcoded Configuration

### Advantages

- Simple implementation

### Disadvantages

- No runtime flexibility
- Frequent redeployment
- Poor scalability

Rejected.

---

## Runtime Script Configuration

Allowing executable scripts to define runtime behavior.

### Advantages

- Very flexible

### Disadvantages

- Security risks
- Difficult validation
- Unpredictable behavior

Rejected.

---

# Compliance

All runtime configuration implementations shall comply with this ADR.

In particular:

- runtime configuration shall reside in the database
- configuration shall be versioned
- configuration shall be validated before activation
- revisions shall increase monotonically
- audit logging shall be mandatory
- authorization shall be enforced server-side
- configuration shall never contain executable code
- secrets shall not be stored in runtime configuration
- effective configuration shall be generated by the backend
- cache invalidation shall use revision information
- configuration schemas shall remain backward compatible whenever possible
- breaking changes shall require new schema versions
- runtime configuration shall remain independent of infrastructure configuration
