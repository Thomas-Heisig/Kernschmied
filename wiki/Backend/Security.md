# Security

The **Security** architecture defines how the Kernschmied backend protects users, data, services, AI providers, and system resources.

Security is not implemented as a single module but as a **cross-cutting architectural concern** that influences every subsystem, including configuration, hierarchy management, model execution, tool invocation, API endpoints, and runtime administration.

A fundamental design principle of Kernschmied is:

> **Dynamic behavior never implies dynamic trust.**

The system is highly configurable, but every runtime decision is evaluated against explicit security policies, authorization rules, validation logic, and stable contracts.

---

# Goals

The Security architecture is designed to provide:

- Secure-by-default behavior
- Defense in depth
- Least-privilege execution
- Strong validation
- Stable trust boundaries
- Backend-authoritative authorization
- Secure runtime configuration
- Auditable administrative changes
- Future enterprise readiness

---

# Security Principles

## Backend Authority

The frontend is considered an untrusted client.

It may:

- display information
- collect user input
- request actions

It may **never**:

- authorize requests
- bypass validation
- select unauthorized providers
- execute tools directly
- modify protected configuration

Every request is verified by the backend.

---

## Explicit Trust Boundaries

The backend clearly separates trusted and untrusted components.

```text
Browser

↓

REST / SSE API

──────────────────────────
Trust Boundary
──────────────────────────

Validation

↓

Authorization

↓

Business Services

↓

Repositories / Providers
```

Only validated requests cross the trust boundary.

---

## Secure by Default

Whenever uncertainty exists, the backend prefers the safest behavior.

Examples include:

- rejecting unknown schema versions
- rejecting unknown action types
- disabling unsupported capabilities
- denying unauthorized requests
- refusing invalid manifests

Unknown behavior should never become implicitly trusted.

# Authentication

Authentication establishes the identity of the caller.

Deployment profiles determine the required authentication mechanism.

Typical profiles include:

| Profile     | Authentication                |
| ----------- | ----------------------------- |
| Development | Simplified local identity     |
| Intranet    | Organization authentication   |
| Internet    | Secure session authentication |

Authentication always precedes authorization.

---

# Authorization

Authorization determines whether an authenticated identity may perform a requested action.

Typical authorization decisions include:

- configuration updates
- hierarchy modifications
- tool execution
- model access
- administrative APIs

Authorization is always enforced by the backend.

---

# Principle of Least Privilege

Every component receives only the permissions it requires.

Examples include:

- repositories only access persistence
- providers only generate responses
- tools execute only approved actions
- configuration services modify only configuration

No component receives unnecessary privileges.

---

# Input Validation

Every external input is validated before processing.

Validation includes:

- JSON structure
- schema compatibility
- identifier format
- enum values
- required properties
- nested objects

Invalid requests are rejected immediately.

---

# Output Validation

Responses generated by the backend also follow validated contracts.

Benefits include:

- predictable APIs
- stable frontend behavior
- provider isolation
- compatibility guarantees

Public contracts remain independent of internal implementation.

---

# Configuration Security

Runtime configuration is treated as trusted application data only after validation.

Configuration updates require:

- authentication
- authorization
- schema validation
- audit logging
- revision updates

Configuration cannot execute arbitrary code.

---

# Manifest Security

Model and tool manifests are validated during bootstrap.

Validation includes:

- schema version
- required fields
- identifier uniqueness
- provider compatibility
- manifest integrity

Invalid manifests prevent registration.

---

# Provider Isolation

Application services never communicate directly with provider implementations.

```text
Chat Service

↓

Model Registry

↓

Provider Backend
```

Provider-specific behavior remains isolated behind stable interfaces.

---

# Tool Security

Tool execution follows a strict security pipeline.

```text
Tool Request

↓

Registry Lookup

↓

Authorization

↓

Input Validation

↓

Execution

↓

Result Validation
```

Only registered and authorized tools may execute.

---

# Hierarchy Security

Hierarchy integrity is protected through backend validation.

Examples include:

- cycle detection
- parent validation
- authorization checks
- schema validation

Hierarchy relationships cannot be modified directly by clients.

---

# Request Validation

Each request passes through several validation stages.

```text
Request

↓

Authentication

↓

Authorization

↓

Validation

↓

Business Logic
```

Later stages assume earlier validation has already succeeded.

---

# Database Security

The database is never accessed directly by API endpoints.

Instead:

```text
Endpoint

↓

Service

↓

Repository

↓

Database
```

Repositories provide the only persistence interface.

---

# Dependency Injection Security

Infrastructure objects are created during bootstrap.

Services receive dependencies through dependency injection rather than constructing them dynamically.

Benefits include:

- deterministic initialization
- lifecycle control
- reduced attack surface
- easier testing

---

# Secrets Management

Sensitive infrastructure values remain outside business configuration.

Examples include:

- database credentials
- API keys
- encryption secrets
- session secrets

Secrets belong in the deployment environment rather than the runtime configuration database.

---

# Environment Configuration

Environment variables should contain only infrastructure bootstrap settings.

Typical examples include:

- deployment profile
- database connection
- logging
- provider endpoints
- secret keys

Business configuration belongs in the database.

---

# Secure Streaming

Server-Sent Events follow the same authentication and authorization rules as ordinary REST requests.

Streaming connections:

- authenticate once
- inherit request permissions
- terminate on authorization failures
- never expose internal exceptions

Streaming does not bypass security controls.

---

# Error Security

Public error responses intentionally hide implementation details.

Example:

```json
{
  "code": "permission_denied",
  "message": "Access denied.",
  "details": {},
  "request_id": "83bf9241"
}
```

Internal stack traces remain server-side.

---

# Audit Logging

Administrative operations generate audit records.

Typical entries include:

- authenticated user
- timestamp
- affected resource
- previous value
- new value
- revision number

Audit logs provide accountability and traceability.

---

# Revision Protection

Configuration, hierarchy, and registries maintain revision counters.

Clients use revisions to invalidate cached state without requiring privileged access to internal implementation details.

---

# Denial-of-Service Considerations

Production deployments should protect against resource exhaustion.

Recommended mechanisms include:

- request size limits
- connection limits
- rate limiting
- streaming timeouts
- provider timeout configuration

These mechanisms are deployment-specific but supported by the architecture.

---

# Logging

Security-relevant events should be logged.

Examples include:

- failed authentication
- authorization failures
- invalid configuration
- provider failures
- administrative changes

Logs should support incident investigation without exposing sensitive information.

---

# Security Profiles

Kernschmied supports multiple deployment profiles.

## Development

Characteristics:

- simplified authentication
- local execution
- developer diagnostics
- reduced operational restrictions

Development should never be exposed publicly.

---

## Intranet

Characteristics:

- authenticated users
- organizational access control
- audit logging
- internal deployment

Suitable for enterprise networks.

---

## Internet

Characteristics:

- HTTPS required
- secure session authentication
- strict authorization
- hardened security configuration
- rate limiting
- secure cookies
- production logging

This profile provides the strongest security guarantees.

---

# Testing

Security should be verified through automated testing.

Recommended coverage includes:

- authentication
- authorization
- validation failures
- manifest validation
- tool permissions
- provider isolation
- hierarchy authorization
- configuration protection

Security testing is part of continuous integration.

---

# Future Extensions

The architecture supports future enhancements including:

# Summary

The Security architecture provides the foundation for trustworthy operation throughout the Kernschmied backend by enforcing backend-authoritative authentication, authorization, validation, provider isolation, repository-based persistence, secure runtime configuration, and explicit trust boundaries.

By combining secure-by-default principles, least-privilege execution, deterministic validation, structured auditing, deployment-specific security profiles, and stable public contracts, Kernschmied remains flexible enough for dynamic, schema-driven applications while maintaining strong security guarantees suitable for enterprise and internet-facing deployments.
